# Internationalization (i18n)

A lightweight, dependency-free UI-language layer. English is the source of
truth and the fallback; Hindi is populated; other Indian languages are
scaffolded and light up once translated. India-first audience.

**Scope is deliberate and narrow: UI *chrome* only** — navigation,
buttons, settings labels. Clinical interpretation copy (biomarker `plain`
text, problem write-ups, risk wording, range explanations) is **not**
routed through this layer. Those need clinician-reviewed translations, not
a dictionary an engineer fills in — see [Why clinical copy is excluded](#why-clinical-copy-is-excluded).

---

## The pieces

| File | Role |
|---|---|
| [`src/app/i18n/translations.ts`](../src/app/i18n/translations.ts) | The dictionaries, the key type, `translate()`, `availableLanguages()`, `LANGUAGES` |
| [`src/app/contexts/LanguageContext.tsx`](../src/app/contexts/LanguageContext.tsx) | `LanguageProvider`, `useLanguage()` → `{ lang, setLang, t }` |
| [`utils/persistence.ts`](../src/app/utils/persistence.ts) | `loadLang()` / `saveLang()` — `dc_lang`, zod-validated |
| [`AppContext.tsx`](../src/app/AppContext.tsx) | Wires `LanguageProvider` (outermost of the context stack); re-exports `useLanguage` |

Current consumers (the first translated surfaces): `BottomNav` (the tab
labels) and `ProfilePage` (the **App › Language** selector). Everything
else renders English until its strings are migrated — and that's fine,
because of the fallback chain below.

---

## How it works

`en` is a `const` object; its keys are the **single source of truth** and
the `TranslationKey` union is derived from it, so `t('…')` is
type-checked — a typo or an unmigrated key is a compile error.

```ts
export const en = {
  'nav.home': 'Home',
  'nav.quiz': 'Quiz',
  // …
} as const;
export type TranslationKey = keyof typeof en;
```

Each other language is a `Partial<Record<TranslationKey, string>>` — it
only needs the keys it has reviewed translations for. Resolution falls
back so a partial language never shows a blank:

```
translate(lang, key)  →  translations[lang][key]   (requested language)
                      ??  translations.en[key]      (English)
                      ??  key                        (raw key — never blank)
```

`translate()` is a pure function (unit-tested in
`i18n/translations.test.ts`); `t()` in the context is just
`translate(lang, …)` bound to the current language.

The selected language lives in `dc_lang` (JSON, zod enum, defaults to
`'en'`). **Unlike the theme, there is no pre-paint bootstrap** — English
is a safe first-paint default and the fallback, so a normal Context with a
localStorage-seeded initial value is enough; switching re-renders.

## Add a translatable string

1. Add the key + English text to `en` in `translations.ts`.
2. Add its Hindi value to the `hi` object (and any other populated
   languages).
3. In the component, replace the literal with `t('your.key')`. Pull `t`
   from `useLanguage()` (or `useLanguage` re-exported from `AppContext`).
   Call the hook **before any early `return`** (hooks rules — see how
   `BottomNav` calls it above its `isMdUp` guard).

That's it — no key registration, no codegen.

## Add a language

1. Populate that language's object in `translations.ts` with reviewed
   strings (it already exists as an empty stub for the Indian languages;
   add new ones to `LANGUAGES` + `translations`).
2. It appears in the Profile picker **automatically** —
   `availableLanguages()` lists English plus any language with ≥1 string,
   so a user can never select a language that would silently render
   English. Empty stubs stay hidden.

## Why clinical copy is excluded

The catalog's `plain` text, the problem write-ups, and the risk wording
are medical statements. Machine- or engineer-translated medical copy is a
liability: a mistranslated threshold or hedge can mislead. So those stay
English until a clinician signs off on translations, and the i18n layer is
intentionally scoped to the non-clinical chrome. If/when reviewed clinical
translations exist, they'd be a *separate, clearly-sourced* dataset — not
folded into this UI dictionary.

The drafted Hindi chrome strings should also get a native-speaker pass
before launch, like any production copy.

---

## Anti-patterns

- **Routing clinical copy through `t()`.** Out of scope on purpose.
- **Adding a language to `LANGUAGES` and shipping it empty as if done.**
  It'll (correctly) stay hidden from the picker, but don't advertise it.
- **Reading `dc_lang` outside `loadLang()`/`saveLang()`.** Go through the
  validated accessors.
- **Hardcoding a label that a user sees** in a translated surface — use a
  key so the language switch stays coherent for that surface.
